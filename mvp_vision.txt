Vision and MVP
•	Product: District-focused standards-based practice app for brief, frequent sessions; launch with South Carolina English II (Reading Comprehension, Grammar, Essay Writing), then expand to Algebra I, US History, Biology and other states.
•	Users: Students (practice + tutor), Teachers (assign + monitor), District admins (reporting/rosters).
•	MVP
•	State/Test/Subject/Standard selection; practice by standard.
•	Question types: MCQ with optional passages/images; Essay (free response with word cap).
•	Assign standards to a class within a date window.
•	Analytics: accuracy and time-on-task overall and by standard, with views for district, school, class, and student.
•	Auth: Google SSO only (Google Workspace for Education supported).
•	AI Tutor: text chat; optional STT and TTS (non realtime), prioritizing cost → latency → quality.
•	Offline tolerance: graceful caching for practice; sync attempts when back online.
•	Compliance: FERPA-minded storage, access control, and retention; use null, not undefined.

Architecture overview
•	Frontend: Next.js 14 (App Router) + TypeScript + Tailwind. Optional Headless UI/shadcn later.
•	Backend/infra: Firebase Auth (Google provider), Firestore, optional Cloud Functions for aggregations, Vercel for hosting.
•	Multi-tenant model: districts -> schools -> classrooms -> users. Users can belong to multiple classrooms; roles: student | teacher | districtAdmin.

export type Role = 'student' | 'teacher' | 'districtAdmin';
export type Difficulty = 'Easy' | 'Medium' | 'Hard';
export type QuestionType = 'mcq' | 'essay';
export interface StandardRef {
  state: string;      // 'SC'
  testId: string;     // 'english-ii'
  subject: string;    // 'English II'
  standardId: string; // 'E2.RC.1.1'
}
export interface Standard extends StandardRef {
  description: string;
  gradeBand?: string | null;
  version: string;
}
export interface McqQuestion extends StandardRef {
  id: string;
  type: 'mcq';
  difficulty: Difficulty;
  passage?: string | null;
  question: string;
  choices: string[]; // prefixed labels optional (A), (B) ...
  answer: string;    // 'A'|'B'|'C'|'D' or index
  explanation?: string | null;
  assets?: { type: 'image' | 'audio'; url: string }[] | null;
}
export interface EssayQuestion extends StandardRef {
  id: string;
  type: 'essay';
  difficulty: Difficulty;
  prompt: string;
  wordLimit: number; // e.g., 500
  explanation?: string | null; // rubric/exemplar
}
export type Question = McqQuestion | EssayQuestion;
export interface Attempt {
  id: string;
  userId: string;
  state: string;
  testId: string;
  subject: string;
  standardId: string;
  questionId: string;
  questionType: QuestionType;
  startedAt: number;     // ms epoch
  submittedAt: number;   // ms epoch
  timeSpentSec: number;  // derived
  correct: boolean | null; // null for essay until scored
  selectedChoice?: string | null;
  freeResponse?: string | null;
  explanationViewed: boolean;
  tutorUsed: boolean;
  classroomId: string | null;
  assignmentId: string | null;
  meta?: { device?: string | null } | null;
}
export interface Classroom {
  id: string;
  name: string;
  districtId: string;
  schoolId: string;
  teacherId: string;
  subject: string;
  state: string;
  testId: string;
}
export interface Assignment {
  id: string;
  classroomId: string;
  name: string;
  standardIds: string[];
  startDate: number; // ms epoch
  dueDate: number;   // ms epoch
  timePerDayMin?: number | null;
  targetQuestions?: number | null;
}
export interface UserProfile {
  uid: string;
  email: string;
  displayName: string | null;
  role: Role;
  districtId: string | null;
  schoolId: string | null;
  classroomIds: string[]; // membership
  allowedDomains?: string[] | null; // for domain-restricted SSO
}

Security and auth
•	Google SSO: Use Firebase Google provider. School/district emails use Google Workspace for Education—same OAuth flow. Enforce domain allowlists per district if needed:
•	On signup, check email.split('@')[1] against district’s allowedDomains. Reject or queue for approval if mismatch.
•	Security Rules principles
•	Students can read/write their users/{uid} and users/{uid}/attempts/*.
•	Teachers can read data scoped to their classroomIds (attempts filtered by classroomId).
•	District admins can read within districtId.
•	Use a users/{uid} doc for role and memberships; optionally add custom claims for fast checks.
•	Prefer null for missing values; forbid undefined.

// Pseudocode for Firestore Rules concepts (to be implemented later)
function isUser(uid)       { return request.auth != null && request.auth.uid == uid }
function profile(uid)      { return get(/databases/$(db)/documents/users/$(uid)).data }
function hasRole(uid, r)   { return profile(uid).role == r }
function inClass(uid, cid) { return profile(uid).classroomIds.hasAny([cid]) }
function sameDistrict(uid, did) { return profile(uid).districtId == did }
// users/{uid}
allow read, update: if isUser(resource.id);
allow create: if request.auth != null;
// users/{uid}/attempts/{aid}
allow read, write: if isUser(resource.parent().id);
// districts/{did}/classrooms/{cid}
allow read: if hasRole(request.auth.uid, 'teacher') && sameDistrict(request.auth.uid, did) && inClass(request.auth.uid, cid)
         || hasRole(request.auth.uid, 'districtAdmin') && sameDistrict(request.auth.uid, did);
// districts/{did}/classrooms/{cid}/assignments/{aid}
allow read, write: if hasRole(request.auth.uid, 'teacher') && inClass(request.auth.uid, cid) && sameDistrict(request.auth.uid, did)
                || hasRole(request.auth.uid, 'districtAdmin') && sameDistrict(request.auth.uid, did);

•	/analytics: tabs for District, School, Class, Student (filter by selection, date range)
•	/auth/callback: Google sign-in handler (if needed)
•	Contexts
•	AssessmentContext: { state, testId, subject, standardId }
•	UserContext: wraps Firebase Auth user + profile doc; normalizes missing fields to null
•	TutorContext: builds subject-aware system prompt; provides ask/stream methods
•	Accessibility
•	Text-to-speech required: use Web Speech Synthesis API by default; server-side TTS fallback later.
•	Keyboard navigation optional now; ensure focus-visible and semantic headings/labels.
AI Tutor, STT, and TTS
•	Prompting: Subject-aware rules; grounded to state/test/standard; avoid LaTeX for ELA unless needed; cite the standard description when available.
•	STT strategy (cost-first)
•	Tier 1: Browser MediaRecorder + upload to API → OpenAI Whisper or faster/cheaper alternative; non streaming (record → send → transcribe).
•	Tier 2: Add streaming STT later if needed (Google STT/Azure). iPad Safari lacks built-in SpeechRecognition; server STT ensures cross-device support.
•	TTS strategy (cost-first)
•	Tier 1: Browser Speech Synthesis API (free, low latency; voice varies by device).
•	Tier 2: Server TTS (e.g., ElevenLabs/Azure/AWS Polly) for higher quality/consistency; cache audio per message for repeated playbacks.
•	Latency controls
•	Short tutor responses, summarization; pre-warm model; debounce user mic control.
Offline tolerance (MVP)
•	Enable Firestore persistence in the client for attempts and questions.
•	Queue attempts writes offline; reconcile on reconnect with idempotent attemptId.
•	Cache selected standards/questions in IndexedDB; fall back gracefully if assets missing.
•	Optional: Next.js service worker for route and asset caching.
Rosters (CSV import)
•	CSV columns (MVP): studentId, firstName, lastName, email, grade, schoolId, classroomName
•	Flow
•	Teacher uploads CSV in /classrooms.
•	Client parses (Papaparse), shows preview + validation.
•	On submit:
•	Create users/{uid} profiles if not exist (derive uid via Firebase Auth only when they sign in; otherwise create “pending user” records keyed by email).
•	Add to districts/{districtId}/schools/{schoolId} if needed.
•	Create/find classroom; update classroomIds for those users.
•	Students sign in with Google; on first sign-in, link their profile by email.
Analytics (MVP)
•	Metrics
•	Accuracy: correct / attempted.
•	Counts: # correct, # attempted.
•	Time-on-task: sum timeSpentSec by filter.
•	Views
•	District → School → Class → Student drill-down.
•	Filters: date range, subject, standard, assignment.
•	Implementation
•	Phase 1: client-queried and computed with indexed queries + pagination.
•	Phase 2: daily Cloud Function pre-aggregations into analytics/* docs for faster dashboards.
Assignments (MVP)
•	Create assignment with name, standards, date window, optional target counts/time.
•	Students see assignment tag in practice flow; attempts link to assignmentId.
•	Dashboard shows completion vs targets; accuracy by standard within assignment.

Best practices we’ll follow
•	Data-driven taxonomies; no hardcoding standards in UI.
•	Validate all imported content with Zod; reject on mismatch; log reasons.
•	Use null not undefined in Firestore; normalize on write.
•	Keep business logic headless (hooks/utils) and style with Tailwind in the app layer.
•	Index queries you depend on; test read paths with production-like data volumes.
Alternatives considered
•	STT/TTS
•	A: Browser-only (free, variable quality). Pros: cheapest; Cons: inconsistent voices, no STT on iOS Safari.
•	B: Server-only (Polly/ElevenLabs + Whisper). Pros: consistent; Cons: cost, latency.
•	C: Hybrid (Recommended): browser TTS default; server STT (non streaming); upgrade to server TTS where needed.
•	Attempt storage
•	A: Only under users/{uid} (simple; add composite queries).
•	B: Mirror to classroom path for teacher queries (better performance; more writes). Recommended B for scale—implement mirroring in a function later.
•	Analytics
•	A: Client-side compute (fast to ship).
•	B: Pre-aggregations in Firestore via scheduled function (faster dashboards). Recommended phased approach: A now, B later.
